## Executed p-code extension experiment (2026-10-18)

**One-factor experiment complete (tool evidence, not actor effectiveness).** Existing proven Ghidra 12.1.4 headless exporter remained unchanged. Added a separate `ExportRawPcode.java` post-script on the *same* source-known stripped x86-64 ELF in the *same* Ghidra analysis session. It enumerates `Instruction.getPcode(false)` SLEIGH-lifted **raw instruction** operations, not decompiler `HighFunction` p-code; records function entries, opcode histogram, bounded first 256 p-code ops/function and varnode operands. It refuses >256 functions, >1,024 instructions/function, >20,000 global operations, >8 varnode inputs/op and existing output overwrite. No project mutation or sample execution.

- [Actual public Ubuntu GHA tool execution #39107388130](https://github.com/SemperSupra/model-spelunker/actions/runs/39107388130): Ghidra tool+script+independent verifier PASS, 16 function identities matched baseline, 523 total raw p-code ops, 85 in dispatcher (all 85 sampled), 20 dispatcher opcode families, normalized relevant-operation total 66 across the file. Public synthetic [bounded JSON artifact #12128752584](https://github.com/SemperSupra/model-spelunker/actions/runs/39107388130/artifacts/12128752584).
- **Semantically consequential distinction:** Ghidra baseline says dispatcher has three callees; its *raw instruction* p-code histogram has two `CALL` ops. Flow and function-derived call relations do **not** have a guaranteed one-to-one relationship with raw op counts. Never conflate these or apply naive count equality as an accuracy score. Observe external thunk/inlining/call-target treatment before interpreting a mismatch.
- Validator independently checks schema, function identity and bounds, sample vs histogram consistency, positive semantic operation presence, and dispatch coverage; it does **not** prove SLEIGH instruction semantics or recovery lift. Added **11 negative controls** (representation confusion, inflated aggregates, fake opcode, tampered attribution, malformed operand, unbounded values etc.).
- After the one-shot pinned Ghidra download and execution, removed the heavyweight probe step from shared portability CI. [Cheap follow-up GHA #39107541186](https://github.com/SemperSupra/model-spelunker/actions/runs/39107541186) PASS includes original source-known 320-vector semantic oracle and independent p-code known-good + 11 negative controls. Explicit `run_public_probe.sh` remains for individually admitted RE studies.

**Outcome:** `raw_pcode_extension=TOOL_QUALIFIED_ON_SYNTHETIC_ELF`; `actor_semantic_lift=UNKNOWN`; `pcode_bytewise_reproducibility=NOT_TESTED`; `additional_model_or_private_cloud_cost=$0`. Next qualifying treatment requires the **same actor/model, tool policy, artifact, verifier and budget**, differing only in (A) baseline decompiler/function summary vs (B) baseline + raw p-code. Model must have source/oracle blocked by OS/network controls before any blind claim. Score independently verified recovered semantics and cost, not number of opcodes or amount of context.

## Source-informed tail-call falsification (compiler to Ghidra)

**The call-count mismatch is now explained rather than merely catalogued.** We independently compiled the exact source-known dispatcher with Clang 17 and confirmed its stripped ELF SHA-256 equals the Ghidra tool-control fixture `4e42cdd47a7a7531470ef9487c66979ce0a90a773c4dddce16151d2ba6430490`. At `-O1`, the dispatcher has two ordinary `call` instructions for affine/rotate helpers plus one optimized *tail `jmp`* for `handler_fold`. Rebuilding with `-fno-optimize-sibling-calls` (single factor) changes that third jump to an ordinary `call`. This accounts for the apparent 3 distinct Ghidra callee targets vs 2 raw p-code `CALL` operations, without a missing function.

Reproducible source-only regression: `qualification/reference/portable-dispatch-v0/test_tailcall_control.py`. On hosted standard GHA Ubuntu Clang 18.1.3, [successful run 39108075288](https://github.com/SemperSupra/model-spelunker/actions/runs/39108075288) independently observed **optimized: 2 calls + 1 tail jump; sibling-call optimization disabled: 3 calls + 0 tail jumps**. Both results are **static compiler/codegen evidence**, not new native behavior tests. The already-qualified standalone semantic oracle still tests the baseline against 320 input/output cases.

**Failure and correction preserved:** An earlier candidate `test_tailcall_control.py` also loaded both synthetic shared libraries through Python `ctypes`, printed the expected static results, then segfaulted during process shutdown on [failed GHA 39108000238](https://github.com/SemperSupra/model-spelunker/actions/runs/39108000238); that run is FAILURE, not a semantic PASS. Removed redundant dynamic-library loads and left runtime behavior to the separate proven oracle. The corrected pure-static study is PASS on run 39108075288. No claim about why Python/loader teardown faulted without further direct evidence. Future agents should treat a function's call-graph edges as distinct from low-level machine CALL opcode count, and investigate optimizer-introduced tail branches before declaring missing behavior.

Do **not** mistake plugin documentation or source inspection for installation/qualification. A plugin is executable code with host process privileges and potential read/write/network capabilities; pin source+binary hash, identify license, constrain workload and egress, reject behavior oracle contamination and provide an uninstall/cleanup path. Prefer built-in supported read-only interfaces before a third-party plugin.

## Cross-language source-informed leverage
Forward compilers provide *known transformation lineage*, not a reverse map guaranteed to exist. Record `source/tree digest -> compiler/tool commit + flags -> forward IR/metadata -> binary digest -> reverse IR/p-code or DEX representation -> recovered semantics -> independent oracle`. Examples:
1. Inlining and dead-code removal: true information erasure; avoid inventing removed source or treating missing helper functions as a decompiler failure.
2. Kotlin `@Metadata` rewrite: distinguish absent/rewritten annotations from incorrect JADX heuristics before patching decompiler output.
3. Swift SIL optimization/ARC and ObjC runtime selectors: distinguish compiler-generated or runtime-mediated dispatch from authored app logic.
4. SLEIGH processor semantics and LLVM TableGen: compare relevant instruction semantics and source-known effects, not IR text equality.
5. Dynamic OS emulation: Qiling/PANDA/Renode observed behavior is conditional on accurate OS/peripheral models, not native runtime proof.

## Sparse execution order and rejection criteria
**P0** Ghidra read-only p-code projection on the *existing* stripped ELF: same input and semantic oracle, one added representation, one bounded CI tool profile. Retain native symbol/function/pseudocode baseline and raw digests; no new Ghidra framework or unrelated 570MB download in generic CI.
**P0 (Android-owned)** AAR `@Metadata` source-matched survival audit and/or JADX read-only visitor pass against one existing precise wrong-overload fixture. Current built-in plugin option switches are terminal negative for those inputs.
**P1** One LLVM opt/Clang controlled variant and, if justified, one Swift SIL/Mach-O native golden, followed by one Renode `.repl` peripheral fixture.
**P2** Frida, Qiling, PANDA, WinDbg, x64dbg and Binary Ninja only when a concrete missing dynamic/symbolic observation remains after simpler static inspection.

For any trial require: tool/source commit and license, actor+tool read/write/execute authority, input digest, raw/normalized output digests, baseline-vs-variant single factor, independent oracle, negative controls, time/storage/cost, `PASS/PARTIAL/FAIL/UNKNOWN`, and measured benefit per added operational complexity. *No blanket installations*, speculative all-tools plugin host, unchecked source forks, SDK redistribution, production sample execution, private hosted minutes or auto-admission. SurgeHalo plugin framework stays blocked by [#8](https://github.com/SemperSupra/surge-halo-private/issues/8).
